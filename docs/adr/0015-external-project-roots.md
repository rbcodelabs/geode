# ADR-0015: External project roots as lightweight workspace mounts

**Date:** 2026-09-04
**Status:** Accepted

## Context

Geode currently opens one filesystem folder as a vault. That single root anchors
the renderer `Vault` model, File Explorer, metadata index, watcher, link resolver,
workspace persistence, and Obsidian-compatible plugin API. Vault files use
vault-relative string paths, and the main process rejects paths that escape the
active vault root.

Claude Threads adds a separate Project concept. Each Project has a
vault-relative `vaultFolder` for its durable notes and artifacts and may have an
absolute `cwdOverride` for agent execution. The resulting `effectiveCwd` can be a
repository or other working directory outside the vault, but those files are not
visible in Geode's File Explorer.

Users need to browse and open files in those working directories without turning
each directory into another knowledge vault. The selected product model is a
lightweight IDE workspace: the vault remains the sole knowledge-management root,
while explicitly attached external directories are read-only workspace roots.

### Constraints

- Existing vault behavior and Obsidian plugin compatibility must remain intact.
- Vault wikilinks, backlinks, metadata, `TFile`, search, and existing plugin APIs
  remain vault-only.
- External paths must never be represented as `../` escapes or synthetic
  vault-relative paths.
- A Threads Project is an integration source, not the owner of core filesystem,
  permission, identity, or explorer behavior.
- Desktop can attach local directories. Mobile cannot assume that a desktop path
  exists or that it syncs through the vault.
- Phase 1 is read-only and validates browse/open demand before funding editing,
  indexing, or a public plugin API.

## Decision

Geode will introduce a core `RootRegistry` above, and separate from, the existing
vault model. The registry owns the stable identity, device-local locator,
availability, capabilities, and containment boundary for every workspace root.

New root-aware boundaries identify a resource as:

```ts
type ResourceRef = {
  rootId: string;
  relativePath: string;
};
```

`rootId` is an opaque, stable UUID generated by Geode. `relativePath` is a
normalized, root-relative slash path. Absolute paths are host-only locators and
are not resource identities.

The active vault is represented in the registry as the distinguished `vault`
root, but the existing renderer `Vault`, `TFile`, vault-relative APIs, and plugin
contracts do not migrate to `ResourceRef`. Root-aware APIs are additive.

Phase 1 adds read-only external roots with these properties:

- kind `project-cwd`;
- capabilities `browse`, `read`, and `open`;
- no `write`, `create`, `rename`, `trash`, `execute`, `index`, or
  `vault-semantics` capability;
- visible under a distinct **Projects** section in the existing File Explorer;
- openable in Geode using root-aware document identity; and
- attachable and reconnectable only through an explicit user grant.

The capability model describes what Geode may do through a root. Agent execution
authority is separate: a Threads Project may already execute in its cwd, but that
does not implicitly grant Geode write access or make an external root trusted.

### Containment and symbolic links

For every operation, the host resolves the registered root and requested target
to canonical real paths before access. The target must equal the canonical root
or remain below it by path-component comparison.

- Lexical traversal, absolute `relativePath` values, NUL bytes, drive/UNC
  injection, and platform-invalid normalization are rejected.
- Directory symbolic links are shown but are not traversable in Phase 1, even
  when their targets remain inside the root. A file symbolic link may be opened
  only when its final resolved target remains inside the same registered root.
- A symbolic link that resolves outside the registered root is shown as an
  unavailable link entry and cannot be traversed or opened in Geode.
- Symlink loops, broken targets, and targets that cannot be canonicalized fail
  closed without aborting the rest of the tree.
- Registering a root through a symlink canonicalizes its locator to the real
  directory while retaining the user-facing chosen path only as a display hint.

This policy prevents an attachment grant from silently widening through a
repository-controlled symlink.

### Root overlap

Canonical paths determine overlap.

- Attaching the exact same canonical directory reuses the existing `rootId` and
  adds or updates the integration reference; it does not create a second root.
- If a requested Project directory is inside an existing external root, Geode
  creates no new root. It reuses the existing `rootId` and records the Project's
  relative base within it.
- If a requested root contains one or more existing external roots, Phase 1 does
  not replace or merge them automatically. Attachment is blocked with a clear
  explanation and the existing roots are named.
- A directory inside the active vault is not mounted externally. Threads keeps
  its Project association, while File Explorer reveals the corresponding vault
  folder through existing behavior.
- The same physical file appears only once in the explorer and uses one canonical
  resource identity.

The asymmetric parent-overlap rule avoids silently broadening previously granted
access.

### Persistence and portability

Root records are device-global, local Geode configuration. A record stores the stable
`rootId`, kind, canonical locator, display label, capability grant, availability,
and optional integration references. A reference includes the originating Geode
vault/plugin instance as well as the Threads Project id, so Project UUIDs from
different vaults cannot collide. It does not store external file contents.

Roots appear in a window only when an integration active in that window
contributes a binding. Root grants are reusable across windows without making
every external root visible in every vault workspace.

### Application ownership and multi-window context

Geode owns one application-lifetime `RootRegistry` engine and one serialized
mutation queue for the device-global store. It must not create independent
per-window registries over the same persistence file.

Window-originated operations use a thin, session-scoped facade derived by the
main process from the IPC sender's current vault session. The facade supplies the
calling window's canonical vault root for overlap checks; renderer input never
supplies a window id or vault authority. A picker or confirmation that outlives
its originating vault session fails as stale and commits no registry change.

The current Electron community-plugin runtime is trusted same-world code with
Node integration. Therefore “vault-only plugin APIs” is an API-support and
compatibility boundary, not malicious-plugin filesystem isolation: Phase 1 adds
no supported external-root surface to Obsidian-compatible `App`, `Vault`,
`TFile`, adapter, or plugin APIs. Strong runtime isolation would require a
separate plugin-sandbox decision.

### Host I/O clarification

- Main owns attach and reconnect ceremonies, including the native picker and
  confirmation. A renderer may suggest a starting location but cannot register
  an arbitrary locator.
- The granted root retains canonical path plus device/inode evidence. Ordinary
  attach reuses a root only while fresh realpath and physical identity still
  match; missing, unavailable, or replaced roots require explicit reconnect.
- Lazy directory enumeration uses fixed 250-entry pages and opaque, ephemeral
  cursors scoped to the sender, root, and directory. Cursors expire after 30
  seconds, with at most 16 live cursors per window.
- Phase 1 bounded reads use read-only file handles, repeated containment and
  physical-identity validation, fatal UTF-8 decoding, an inclusive 2 MiB byte
  limit, and rejection of NUL-containing content. Special filesystem nodes are
  never openable.
- These checks fail closed on detected replacement but are not an `openat`-style
  sandbox against a hostile local process. A stronger descriptor-relative
  traversal design is a revisit condition, not implicit Phase 1 scope.

Portable plugin state may retain a Project id, label, repository hint, and legacy
cwd path, but a local path never establishes authority on another device. A moved,
missing, or ungranted directory remains as a disconnected root until explicitly
reconnected.

## Options considered

| Option | Advantages | Costs and failure modes |
|---|---|---|
| Make the vault truly multi-root | Uniform file and knowledge semantics | Requires root-awareness across links, metadata, graph, plugins, caches, and all `TFile` consumers; high compatibility and migration risk |
| Add a separate repository explorer | Small initial surface | Duplicates navigation and makes later convergence harder unless it still adopts core resource identity |
| Let Threads render a plugin-owned virtual tree | Can ship within the plugin | Gives a plugin core filesystem/security duties; open resources become dependent on plugin lifecycle; other integrations cannot reuse it |
| **Core registry with lightweight mounted roots** | Integrated navigation, reusable foundation, preserved vault invariants | External files intentionally have fewer features; the UI must make that boundary obvious |

## Consequences

### Benefits

- Users can navigate Project files without leaving Geode.
- The vault remains compatible with Obsidian's single-vault model.
- Root identity no longer depends on an unstable absolute path.
- Filesystem grants and containment live in the host rather than a community
  plugin.
- The same foundation can later support manual mounts or provider-backed roots
  without committing Phase 1 to those features.

### Costs

- The editor and workspace need an additive root-aware document path alongside
  their existing `TFile` path.
- External Markdown may look editable/readable like Markdown while deliberately
  lacking vault wikilinks, backlinks, metadata, and plugin behavior.
- Refresh and persisted tabs must handle unavailable roots.
- Desktop and mobile expose different root availability without pretending that
  external directories sync.

## Risks

The riskiest assumption is that browsing and opening Project files supplies most
of the value. If users immediately require editing, project-wide search, or full
knowledge semantics, Phase 1 will validate the wrong slice.

Other risks include confusing external Markdown with vault notes, expensive
directory enumeration in large repositories, unstable identities if deduplication is not based on
canonical paths, and integrations accidentally treating browse permission as
execution or write authority.

## Revisit conditions

Revisit this decision if validation shows that users primarily need:

- full wikilinks, backlinks, metadata, or plugin behavior across roots;
- repository editing rather than browse/open;
- remote provider-backed project trees on mobile; or
- multiple first-class knowledge roots in one window.

Any such expansion requires a follow-up ADR; it does not widen this decision
implicitly.
