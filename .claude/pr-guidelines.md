# PR Guidelines — Geode

Generated by the pr-checklist skill. Edit freely.

## Commands

| Task | Command |
|---|---|
| Type-check | `npm run typecheck` |
| Unit tests | `npm run test:unit` (vitest) |
| E2E tests | `npm run test:e2e` (builds, then runs the Playwright Electron smoke test) |
| Build (sanity check) | `npm run build` |
| Full gate (everything above) | `npm test` |
| Clean up after an interrupted e2e run | `npm run e2e:kill` (add `-- --dry-run` to preview) |
| Screenshots | none — see "Visual Verification" below |

## Test Gate

The test harness (vitest unit tests + a Playwright Electron smoke test)
shipped as the **NOW** item on the Compass roadmap. `npm test` runs
`vitest run && npm run build && playwright test` and is a required gate
before opening a PR, alongside typecheck — matching the standard Steps 2–3
of the base pr-checklist skill.

```bash
npm run typecheck
npm test
```

**Requirements:**
- All existing unit and E2E tests pass — do not skip or delete tests to
  force a green suite
- Unit tests (`tests/unit/`) cover the pure data layer: `parseMetadata` and
  link resolution (`getFirstLinkpathDest`) in `src/renderer/metadata-cache.ts`,
  search query parsing/matching (`parseQuery`/`matchFileAgainstTerms`) in
  `src/renderer/views/search-view.ts`, the fuzzy matcher (`fuzzyMatch`) in
  `src/renderer/modals/modals.ts`, and rename link-rewriting
  (`rewriteWikilinksForRename`) in `src/renderer/rename.ts`. New pure
  logic added to these areas needs new unit tests covering the happy path
  plus at least one edge case.
- The E2E smoke test (`tests/e2e/smoke.spec.ts`) boots the built app against
  `test-vault/`, opens a note, and asserts Live Preview renders correctly
  with no console errors. Any change that alters this flow (vault
  auto-open, file explorer, Live Preview rendering) must keep this test
  green — extend it rather than deleting assertions if the change is
  intentional.
- If the test command crashes before running any tests (tooling error, not
  an assertion failure): this is a tooling bug, not a test failure. Stop
  and fix the tooling before treating any work as done.

## Visual Verification

Geode is an Electron desktop app, not a responsive web app — the base
skill's default viewport matrix (1280x800 / 390x844 mobile) doesn't apply.

Whenever any UI is touched (renderer, CodeMirror integration, panes,
modals, settings, etc.):

- [ ] Run `npm start` and manually exercise the changed flow in the live
  Electron window
- [ ] Confirm the change works against the demo vault in `test-vault/`
- [ ] No fixed window-size matrix required — resize the window ad hoc if
  the change is layout-sensitive (e.g. sidebar/pane resizing) to confirm
  it holds up at both a small and a maximized window size
- [ ] No visual regressions in the changed area vs. pre-change behavior

## Docs Location

User-facing / spec docs live in `docs/spec/`. These are reverse-engineered
technical specification references for Obsidian's documented behavior — if
a change alters behavior that a spec page documents as the target, update
that page.

**Do not** treat `docs/spec/00-overview.md` § "Implementation status
(v0.1)" as something to update for roadmap/status purposes — that section
is a frozen historical snapshot. Roadmap and status now live in Compass
(see `pm-config.md`).

## Issue Tracker — Compass, not Linear

This repo tracks roadmap/delivery work in Compass
(`https://compass.rbcodelabs.com/rbcodelabs/geode`), not Linear.

- [ ] If this PR closes out or advances a Compass roadmap item, update that
  item's status in Compass (e.g. mark NOW item as shipped, log progress)
  before or immediately after opening the PR — don't batch it for later.

## Project-Specific Gates

- Compass is the source of truth for roadmap/priority — see `pm-config.md`
  and `CLAUDE.md`. Don't resurrect `docs/spec/00-overview.md`'s frozen
  status list or the old vault status-review note as planning input.
- Solo repo: for docs-only or low-risk changes, merging a short-lived
  branch straight to `main` (no PR) is acceptable, matching current
  practice. Use a PR when the change touches app code and benefits from a
  second look or a deploy/build check.
